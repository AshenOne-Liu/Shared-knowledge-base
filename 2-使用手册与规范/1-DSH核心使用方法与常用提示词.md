# DSH 核心使用方法与常用提示词

## 什么时候使用/不用 Agent

- 人工负责：目标描述 + 审查产出。
- Agent 负责：项目开发。

> **用 Agent 去做它大概率做砸的事，是最大的时间浪费**
> 比如需要高度创意判断的架构决策、或极细粒度的样式微调

**DSH 在这个项目中“适合做”与“不适合做”的事：**

- 适合交给 DSH 的：项目脚手架、样板代码（数据模型、Repository、Provider）、批量文件重构、运行 `flutter analyze` / `flutter test` / `flutter build` 并修复报错、生成配置文件和构建脚本、编写测试代码。这些任务的共同特征是规则明确、可验证、无需视觉判断。
- 需要你亲自主导的：冲突解决策略的决策、同步可靠性的验收标准、UI/UX 的视觉打磨、各平台真机上的体验验证、以及每一个阶段完成后对 `diff` 的审查。DSH 的自主性很高，但它不“知道”一个 Todo 应用在用户体验上什么算好。比如你之前选 Flutter 是为了降低跨平台维护成本，DSH 的作用是加速你在 Flutter 上的编码循环，而不是替代你对产品质量的判断。

## 核心交互方法

### 消息投递语义：Enter、Tab、Ctrl+Enter 的区别

DSH 在 Agent 正在工作时，对“你再发一条消息”有三种处理路径，理解这个区别能大幅减少来回等待的挫败感：

- **Enter（steer）** ：把你的消息送进**当前正在运行的回合**，Agent 在下一步边界领取。适合“方向微调”，比如“同步逻辑先跳过，只做本地存储”。
- **Tab（follow-up）** ：排入队列，**等当前回合结束后**再处理。适合“这件事之后再做”，不打断 Agent 当下的工作。
- **Ctrl+Enter（interrupt）** ：**立即打断**当前回合，把你的新消息作为当前指令。适合发现 Agent 走错方向、或者你想紧急插入更高优先级的事。

待办软件开发中，最常见的误用是在 Agent 正在写代码时反复用 Enter 插话，导致上下文被稀释。**方向性调整用 Ctrl+Enter 说清楚，补充性事项用 Tab 排队，是最节省上下文的方式。**

### 斜杠命令：高频操作的快捷入口

在输入框中输入 `/` 会弹出当前已注册的命令列表。对于你的项目，最值得在起步阶段就熟悉的命令是：

**`/plan` —— 带需求进入计划模式**
直接输入 `/plan 我要给待办软件增加“重复任务”功能，先只做设计和影响分析`，DSH 会进入计划模式进行只读分析，输出方案供你审阅。这是你控制“大功能”节奏的核心命令。

**`/goal` —— 声明当前阶段的长期目标**
例如 `/goal 完成待办软件 MVP 的本地核心循环：创建、编辑、完成、删除、按截止日期排序`。设置后，Agent 在后续每轮对话中会主动围绕这个目标推进，跑题时也会自行绕回。一个阶段只维护一个 `/goal`，阶段切换时用 `/goal edit` 更新。

**`/compact` —— 会话变长时压缩上下文**
当一个会话已经进行了较长时间，上下文开始冗余时，`/compact` 会把关键信息整理为紧凑摘要，Agent 带着摘要继续工作，而不是被历史对话拖累。待办软件的 UI 细节讨论容易产生大量来回，这个命令在你觉得 Agent “开始健忘”时使用。

**`/export` —— 导出当前对话**
需要把某次讨论留存为决策依据时，`/export` 会下载完整的对话记录压缩包。适合在完成一个重要技术讨论（比如“同步方案选型”）后导出一份，放入项目的决策记录目录。

### `@`文件引用：精准投喂上下文

- 在消息任意位置输入 `@` 会打开文件补全菜单，选中文件后，其内容会自动附加到消息中发送给 Agent。
- 对于每次开工前都要阅读的文档，这个功能的最佳用法不是“每次手动选文件”，而是**在 `AGENTS.md` 中预先写好“开工先读哪几份文档”的规则**，让 Agent 自动按路径读取，减少你手动 `@` 的频率。
- 手动 `@` 保留给“临时需要 Agent 看一份计划外文件”的场景，比如“@docs/contracts.md 看一下 TodoItem 的类型定义，确保新代码不破坏它”。

### 会话交接：长会话的收尾机制

- 当会话变长、Agent 开始“降智”或上下文接近上限时，可以借助社区插件完成交接。
- 如果你不安装插件，也可以用手动方式实现同等效果：在会话结束前，让 Agent 把“当前状态 + 下一步”追加到 `docs/PROGRESS.md`，新会话开始时让它先读这份文件再开工。对个人开发者，**手动交接 + 进度文档**是最低成本的可持续方案，插件可以在会话频繁超长后再引入。

### DSH 的 7 个典型行错误为，和你的应对

| 行为 | 表现 | 你的应对 |
|---|---|---|
| **自信地错** | 说“已修复/应该可以”，但没验证 | 要命令、日志、复现步骤；“先证明，再结论” |
| **顺手多做** | 改需求之外的文件、加你没要的功能 | “只做 X，别动 Y；要做先问我” |
| **忘记旧决定** | 又提出已经被否掉的方案 | “这个之前定了不做，依据在 SPEC §7；先看文档” |
| **沙箱里硬试** | 同一个报错反复换写法 | “两次没解决就停，申请完全权限或交接” |
| **环境问题当产品问题** | 把沙箱限制说成“软件 bug” | “先分清是环境还是产品，给证据” |
| **报喜不报忧** | 只说成功，不说失败项/限制 | “列出失败的、没验证的、有风险的” |
| **过度设计** | 一上来就抽象、加配置项 | “先最小实现，能跑通再优化” |

---

### 权限与审批：什么时候点“同意”

DSH 在沙箱里跑，需要**完全权限**才能：写 `obj/bin`、改注册表、建系统目录、启动需要正常权限的程序、读系统计数器。

### 判断标准

| 情况 | 建议 |
|---|---|
| 命令只影响工作区、且是构建/发布 | 同意 |
| 要写 HKCU、删文件、装东西 | 先问“具体写/删什么”，再决定 |
| 要访问工作区外、或联网下载 | 谨慎；要求说明用途 |
| 理由含糊、范围很大 | 拒绝，要求拆小 |

---

### 沟通风格：直接设定，不要客气

DSH 会跟着你的要求调整风格。直接说：

- **要结论**：“先给结论，再展开，不超过 10 行。”
- **要细节**：“展开讲，给文件路径和行号。”
- **要中文**：“用中文回答。”
- **不确定就说不确定**：“没验证的就说没验证，不要猜。”
- **不要客套**：“不用总结，直接说结果。”

## 关键动作与提示词

> 按照使用场景分类

### 一页速查卡

```text
开工：先复述 → 再方案 → 后代码
范围：只做 X，别动 Y，超范围先问
验收：步骤 + 证据 + 未完成项
卡住：两次没解决 → 停 → 最小复现 → 交接
上下文：50% 收口，70% 只做小修
发布：退出程序 → 脱敏扫描 → 文件清单 → 打包 → 实测
提交：只看 publish/，逐个文件确认
隐私：密钥不进对话，内部文档不进公开仓库
```

### 想法发散

> 这个阶段主打一个灵活、要求想法必须发散，先到更多可能性，所以没有一套固定话术。最终可以让Agent整理一份清晰的想法列表，用于下一步收敛。

```text
我们做一个新项目：<一句话>。技术栈<…>，不能<…>。先不要写代码，帮我把需求整理成 SPEC 草案（功能、明确不做的事、验收标准、技术决策点），我们逐条确认。
```

### 快速规划

> 将「模糊意愿」压缩为一个「可被 DSH 执行的最小范围定义」。

**DSH 用法：**

- 在计划模式下，用 `/goal` 设定阶段目标，然后让 Agent 帮你做结构化梳理，而不是直接生成代码。例如：

```markdown
/plan 帮我把“类似微软 Todo 的软件”拆解为：目标用户、核心场景、MVP 必须有的 5 个功能、明确不做的 5 个功能、跨平台策略（桌面优先还是移动优先）。输出一张表，不要写任何代码。
```

- 这一轮对话的目的不是让 Agent “告诉你做什么”，而是**逼迫你自己把范围写下来**。Todo 类产品的功能直觉太强，容易让人跳过定义直接开写，结果做了三个月发现同步没做、平台只覆盖了一个。

**产出文档：**

- `docs/PROJECT_STATE.md` 和 `docs/TODO.md` 的初始版本。
- `PROJECT_STATE.md` 写明当前阶段、MVP 功能边界、跨平台决策（比如“第一阶段只做桌面端，移动端后置”）；
- `TODO.md` 列出从立项到 MVP 交付的粗粒度任务清单。

### 计划与规划

**第一条消息用只读任务开头**：DSH 官方快速开始建议第一次任务先给 read-only 指令，确认它理解了工作区再授权写入。你在 `/plan` 下的第一条消息正好满足这一点。

```text
/plan

先读 AGENTS.md、PROJECT_STATE。给出下一步计划，不要写代码。
```

#### 技术选型

```text
每个技术点给我1-2个备选方案，以及各自的影响和推荐，由我来确定。
```

### 核心开发

#### MVP 骨架与核心循环（主要编码阶段）

**目标**：跑通“创建 → 查看 → 编辑 → 完成/删除”这一条最短路径，数据能持久化。

**DSH 用法**：从计划模式切回**默认模式**，让 Agent 按 `TODO.md` 中的子任务逐项执行。这个阶段的关键纪律是**一次只让 Agent 推进一个可验证的子任务**，而不是“把 MVP 写出来”。一个可验证的子任务长这样：

> “实现 `TodoItem` 的数据模型和本地存储层，要求：重启应用后数据不丢失；先写一个最小测试验证创建和读取。”

每完成一个子任务，让 Agent 更新 `docs/PROGRESS.md`（当前进度）和 `docs/TODO.md`（勾选完成项）。**不要让“完成”停留在聊天记录里**，否则下一个会话 Agent 无法可靠地知道什么已经做完了。

**产出文档**：`docs/architecture.md` 的极简版本（模块骨架：UI / 状态 / 存储 / 平台适配），以及 `AGENTS.md` 的项目根版本（此时只需要几条硬规则：技术栈、包管理器、测试命令、不要碰哪些目录）。`docs/contracts.md` 在这一阶段必须建立，写清 `TodoItem` 的字段和语义——这是后续所有功能扩展时 Agent 不能破坏的硬边界。

#### 功能扩展（最容易失控的阶段）

注意：瀑布式开发不太容易会出现这种情况，所有功能都应该按照spec.md和plan.md开展。但是如果采用敏捷开发，功能扩展才是常规情况。此时一定注意同步更新文档，避免项目范围失控。

**目标**：在核心循环稳定的基础上，按优先级加入待办软件的必要能力（截止日期、排序、标签、搜索等），并处理跨平台一致性。

**DSH 用法**：**每一个中等以上功能，先用 `/plan` 过一遍**。例如：

> `/plan 我要增加“重复任务”，但不确定重复规则的数据模型和 UI 入口应该怎么设计。先只做分析和方案对比，不要改代码。`

计划模式下的输出是“方案审阅材料”，你确认后再切默认模式执行。这个阶段最容易出现的失误是**同时推进 3 个以上功能分支**，导致每个都半成品、每个都需要 Agent 在上下文中来回切换。**一次只让一个功能处于“正在开发”，其余留在 `TODO.md` 的待办区**，是这一阶段最重要的纪律。

平台适配（快捷键、路径处理、深色模式）可以作为独立子任务批量处理，但仍需每次只推进一个平台的一个切面，而不是“把 macOS 和 Windows 的适配一起做了”。

**产出文档**：`docs/PROGRESS.md` 成为高频更新的文件；`docs/decisions.md`（或轻量 ADR）开始积累，记录“为什么选这个同步策略 / 为什么不做云同步 / 为什么用这个状态管理方案”。`docs/architecture.md` 随模块增加而更新，但**只写“现在是什么”**，不写“以前怎样”。

#### 打磨与发布准备

**目标**：从“能跑”到“一个陌生人可以独立使用而不困惑”。

**DSH 用法**：这个阶段减少“生成新代码”的比重，增加“让 Agent 站在陌生用户角度审查”的比重。例如：

> “读 `docs/architecture.md` 和核心 UI 代码，列出 5 个最可能让第一次使用的用户困惑的地方，按严重程度排序，不要直接改。”

打包、签名、商店素材、隐私政策初稿这些**确定性高、创造性低**的任务，可以交给 DSH 按清单执行。但要记住：**发布相关的账号、证书、支付准入等事务，DSH 不能替你操作**，它只能生成文档和检查清单。

**产出文档**：`04_Operations/` 下的上架文案、截图清单、定价笔记；`05_Legal/` 下的隐私政策初稿；`06_Releases/` 下的构建产物（用 `.gitignore` 排除）。`docs/DEBT.md` 如果尚未建**立，在这一阶段补上，列出已知的脆弱点和“发布后再修”的事项。**

### 变更

> 先评估，再动手
> 需求变更是常事，但要防止“改一处、崩三处”。

#### 质疑与纠错

```markdown
- 这个不对：现象是 <…>，期望是 <…>。先别改，告诉我你的判断依据。
- 你刚才说的和我看到的不一致，贴一下对应的日志/代码。
- 这个结论你验证过吗？没有的话，先验证再回答。
```

#### 需求变更

```markdown
我决定进行需求变更，给我新的实施计划、影响、验收项目，让我确认，先不编码。
- 我要改需求：<新需求>。
- 先评估影响：要改哪些文件、哪些已验收功能会受影响、文档要更新哪里。
- 给我新的实施计划、验收清单。
- 先不要编码，等我确认。
```

```text
确认你的计划，可以开始编码，注意同步更新相关文档。
```

#### 小修小补

```text
需要作如下修改：

1. <具体改动1>。
2. <具体改动2>

完成后告诉我验证方法。
```

#### 破坏性操作

```text
这个操作如果是破坏性操作，需要先备份，或在临时副本上修改。
```

### 交接

#### 什么信号说明“该交接了”

- 对话已经很长，DSH 开始重复问已经说过的事；
- 它开始引用过时的结论（比如还在说“设置里有清理按钮”）；
- 它读一份大文档要分好几次，或者反复读同一个文件；
- 一个阶段做完了、下一个阶段还没开始——这是最佳交接点。

#### 50% 规则

| 水位             | 你该做什么                           |
| ---------------- | ------------------------------------ |
| < 30%            | 正常推进，可以让它读大文件           |
| 30–50%          | 别再开新功能，收口当前阶段           |
| **≥ 50%** | **让它编译通过、写交接、迁移** |
| ≥ 70%           | 只做小修；不要接新需求               |

#### 交接前，你要做三件事

1. 确认**当前改动已编译通过**（半成品也要能编译）；
2. 告诉它**哪些是未决问题**（别让新会话猜）；
3. 检查交接里**有没有可复制的命令**（构建、运行、验证）。

#### 中途交接

```text
上下文已经过半。先别开新功能：把当前改动编译通过，然后按五段式生成交接文档——Goal / Current state / Key decisions / Key files / Next step。未决决策点单独列出来。
```

#### 阶段完成交接

```text
以上功能验收完毕，现在暂停推进计划，先检查并更新项目文档，然后生成交接文档，准备开始交接。
```

#### 新会话开场

**要求理解交接：**

```text
我们继续项目开发。先阅读 HANDOFF.md、AGENTS.md、SPEC.md。
只关注阶段 N 的任务。
简要复述当前状态和下一步。让我确认你已经正确理解。不编码。
```

**确认理解交接，开始准备计划：**

```text
确认你已正确理解。现在先给我一个极简的实施计划，等待我确认，不编码。
```

**确认计划，开始编码：**

```text
确认，可以开始编码。
编码完成后给我手动验证的步骤和标准。
```

### 验收

> 如何判断“真的做完了”

#### 要三类证据

| 类型       | 例子                                                      |
| ---------- | --------------------------------------------------------- |
| 可复现命令 | “运行 `dotnet build ... -c Debug`，0 警告 0 错误”     |
| 客观数据   | “60 秒 CPU 增量 0.016 秒；私有内存稳定在 182MB”         |
| 演示步骤   | “打开设置 → 拖通透度到 100% → 深色壁纸下不应是纯白块” |

#### 视觉类验收：你负责，DSH 看不到屏幕

DSH **没有眼睛**，看不到你的桌面。所以：

- 让它给**具体操作步骤**，你照做并反馈现象；
- 需要它判断时，描述清楚：“左边托盘区偏右 2px”“浅色任务栏上图标太淡”；
- 必要时截图发它（如果客户端支持）。

#### 数据类验收：让它贴数字

> 不要只说“性能没问题”，给我采样命令和结果数字。

#### 项目最终验收

```text
检查项目进展，确认是否还有未验收的任务。
全部完成验收后，更新项目文档。
```

### 脱敏

#### 让 DSH 做的四件事

1. **扫描私有信息**：本机路径（`D:\...`）、用户名、机器名、邮箱、内部文档名；
2. **确认内部文档不在仓库里**（ROADMAP / CONVENTIONS / AGENTS / 交接）；
3. **给你一份扫描结果**，而不是“已脱敏”。

#### 话术


## 如何提高工作质量

### Prompt Engineering（提示词工程）

与 AI 交互需要通过提示词告诉 AI「角色、任务、要求、如何交付」等信息。

通过设计和优化提示词，来改善模型表现的过程就是 Prompt Engineering。

#### Agent 配置

维护好自己的 `agents.md`，即工作说明。把长期适用的要求提前写好。包括：

1. 全局级别配置

   > 即通用的做事规则
   >
2. 项目级别配置

   > 放在项目目录里。补充项目的具体要求。比如技术栈、文件怎么组织、怎么测试
   >

#### 怎么写好提示词

从“聊天”转向“写需求文档”。最关键的认知转变是：**提示词不是聊天，而是一份简洁但完整的需求文档**。

对 Coding Agent 而言，它本身就是一个“读文件 → 改代码 → 跑命令”的循环，**不需要你在提示词里教它“请一步步思考”或“请先搜索代码”**——这些能力已经内置，重复要求只会浪费 Token 并干扰判断。

一个高效的编码提示词，骨架是 **“目标 → 上下文 → 约束 → 成功标准”**，复杂任务再加一条 **“非目标”** 来划定禁区：

| 要素               | 要回答的问题             | 反面示例             | 正面示例                                                                                                        |
| ------------------ | ------------------------ | -------------------- | --------------------------------------------------------------------------------------------------------------- |
| **目标**     | 当前是什么，要变成什么？ | “帮我优化一下代码” | `save_file()` 当前会把空内容也写入磁盘，改为空内容时弹出确认框且不写入                                        |
| **上下文**   | 哪里相关？怎么复现？     | “有个 bug”         | `@src/notepad.py` 第 47 行，运行 `python app.py` 后点击保存空文件即可复现，报错原文：`PermissionError...` |
| **约束**     | 什么不能动？             | （不写）             | 只改 `save_file` 函数，不要动 UI 层，不要引入新依赖                                                           |
| **成功标准** | 怎样算做完？             | “改好就行”         | 运行 `pytest tests/test_save.py` 全部通过，手动测试空内容保存不再写入磁盘                                     |

#### 一个特别适合代码 Agent 的技巧

在“上下文”中直接贴报错原文 + 用 `@path` 指向相关文件，比用自然语言描述代码准确得多，因为模型读代码比读你的描述更准。

对于 DeepSeek 模型，官方实践还提示少用 Few-shot 示例，直接把任务边界和验收标准写清楚效果更好。

### Context Engineering（上下文工程）

#### 给模型组织好他这次工作需要的信息

**维护好上下文文档**
尤其是做大项目。包括项目目标、已经确定的方案、当前进度、接下来要做什么（比如 DSH 的 Billion Context 插件可以帮助管理和压缩上下文）。

**多开新对话**
项目很大，不代表所有事情都要在一个对话里完成。建议按功能、按阶段拆解对话。一个工作或阶段完成后，就更新到上下文文档里。再新开一个对话让 AI 读完继续干。好处如下：

- 以保证项目持续推进。
- 每个对话也都有清楚的任务。
- 保持整个项目的连续性。

#### 管理好 Agent“眼前”和“手边”的信息

Agent 变“笨”，往往不是模型不行，而是上下文腐烂，即无关信息挤占了注意力，关键信息被淹没。你需要在两个维度上主动管理：

**会话策略：把“规划”和“执行”拆开**
面对模糊需求时，先开一个规划会话，让 Agent 出方案、你审方案；方案确定后，再开一个干净的执行会话去落地。这能显著降低跑偏率。不要把“画出整只猫头鹰”的期望压在一个超长会话里。

**上下文锚点：用文件固化“真相”。**
在你的项目根目录建一个 `AGENTS.md`（或 `CLAUDE.md`），作为 Agent 的“活地图”。初始只写三样东西：项目是什么、怎么跑起来、怎么验证。之后每当 Agent 犯一个错，就在这个文件里追加一条对应规则。例如：

- Agent 改了不该改的配置文件 → 追加“不要修改 `config/` 下的任何文件”
- Agent 提交前没跑测试 → 追加“修改后必须运行 `pytest`，通过后方可声明完成”

这个文件要保持在“地图”形态（约 100 行以内），规则多了就拆到 `docs/` 子文档，避免它本身变成挤占上下文的负担。

### Harness Engineering（驾驭工程）

包括工具怎么执行、结果怎么传回来、出错后怎么办、任务怎么继续。

让系统在你设定的规则下持续稳定安全可控地推进任务，最终交付结果。

#### 让“这次做对”变成“每次都做对”

这是高质量开发最核心、也最容易被忽视的一层。它的心法只有一句话：Agent 每犯一次错，就工程化一个机制，让它永远不再犯这个错。

你在对话里纠正一次，只是“消费”了一次教训；把它变成一个文件、规则或脚本，才是“投资”。

| 旧反应（消费）                        | 新反应（投资）                                                   |
| ------------------------------------- | ---------------------------------------------------------------- |
| 在对话里说“不对，应该先跑 `lint`” | 把 `lint` 命令写进 `AGENTS.md` 的验证段                      |
| 手动改掉 Agent 生成的违规代码         | 加一条 `lint` 规则或 `pre-commit hook`，让违规在提交时被拦下 |
| 每次人肉检查“有没有忘记写测试”      | 把测试命令写成 Agent**必须执行的自验证回路**               |

#### 最关键的单项投资：给 Agent 装上“自验证回路”

如果你给 Agent 一个验证自己工作的方法，它多半会自己修好错误。对于记事本这类小项目，一个极简的回路就够了：

- **写代码** → 让 Agent 在完成修改后**必须运行 `pytest` 和 `ruff check`**（或你选用的 `lint` 工具），把命令写进 `AGENTS.md` 的“验证”段。
- **写 UI** → 如果有条件，给一个截图脚本或浏览器检查命令，让 Agent 对比预期效果。
- **通用原则**：**把验收标准前置到任务开始时给出**（就在提示词的“成功标准”里），而不是等 Agent 做完后由你人肉验收。
