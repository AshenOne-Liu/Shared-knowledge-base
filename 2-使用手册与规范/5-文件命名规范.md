# 文件名风格规范
你观察到的混乱，根源在于命名规范通常**分层**：**文件系统层面**和**代码符号层面**遵循的逻辑不同，不同语言生态也有各自的历史约定。下面这份整理，先给出“风格速查”，再按类别拆解具体规则和背后的原因。

---

### 命名风格速查

| 风格 | 格式 | 典型示例 | 主要适用场景 |
|---|---|---|---|
| **camelCase**（小驼峰） | 首词小写，后续首字母大写 | `getUserById` | 变量、函数、方法（JS/TS/Java/Go 等） |
| **PascalCase**（大驼峰） | 所有词首字母大写 | `UserService` | 类、接口、类型、枚举 |
| **snake_case**（蛇形） | 全小写，下划线分隔 | `user_name` | Python/Rust 变量与函数；SQL 字段；部分语言的文件名 |
| **kebab-case**（烤串） | 全小写，连字符分隔 | `user-profile.ts` | **文件、文件夹**、URL、CSS 类名 |
| **UPPER_SNAKE_CASE** | 全大写，下划线分隔 | `MAX_RETRY_COUNT` | 常量、环境变量 |
| **SCREAMING-KEBAB** | 全大写，连字符分隔 | `MAX-RETRY-COUNT` | 极少使用，除非特定框架强制 |

---

### 一、文件夹与文件命名 

**核心原则：全小写 + 连字符（kebab-case）作为默认。**

这是目前跨语言、跨平台最稳妥的选择，原因有两点：

1. **跨平台安全**：Linux 文件系统大小写敏感，Windows/macOS 默认不敏感。`UserService.ts` 和 `userservice.ts` 在 Linux 上是两个文件，在 Windows 上却可能引发混淆或 Git 合并冲突。全小写 + 连字符可以彻底规避这类问题。
2. **可搜索性与 SEO**：Google 的开发者文档风格指南明确指出，搜索引擎将文件名中的连字符识别为单词分隔，而下划线通常不被识别；小写也能让文件搜索更稳定。

因此，Google、华为等团队的规范以及众多开源项目都推荐：

> **文件夹 / 文件：全小写，单词之间用连字符 `-` 分隔。**
> 示例：`user-management/`、`api-reference.md`、`task-service.ts`。

**需要留意的例外情况**：

- **Python 生态**：PEP 8 推荐 Python 脚本文件名使用**小写 + 下划线**（`snake_case`），因为 Python 模块名本身就是标识符，连字符在 `import` 语句中非法。在纯 Python 项目中，文件名遵循 `snake_case` 是合理的。
- **特殊约定文件**：`README.md`、`LICENSE`、`CHANGELOG.md`、`CONTRIBUTING.md` 等社区标准文件，保留其**全大写**的惯例，不要强行改成小写。
- **生态强制目录**：`node_modules/`、`.github/` 等由工具或平台约定，保持原样即可。
- **避免临时性命名**：文件夹名应反映**持久的领域概念**（如 `auth`、`billing`、`orders`），避免 `new`、`temp`、`copy`、`v2`、`final` 这类会随时间失效的名称。

---

### 二、代码元素命名

#### 变量与函数：跟随语言主流

| 语言 | 变量 / 函数 | 常量（全局） |
|---|---|---|
| JavaScript / TypeScript | `camelCase`（`getUserById`） | `UPPER_SNAKE_CASE`（`API_BASE_URL`） |
| Java | `camelCase`（`localValue`） | `UPPER_SNAKE_CASE`（`MAX_STOCK_COUNT`） |
| Python | `snake_case`（`get_user_by_id`） | `UPPER_SNAKE_CASE`（`MAX_RETRY_ATTEMPTS`） |
| Go | `camelCase` | 导出常量用 `PascalCase`；私有常量 `camelCase` |
| Rust | `snake_case` | `UPPER_SNAKE_CASE` |

上表综合自多个语言命名规范对照表以及阿里 Java 规约。核心逻辑是：**在一个语言生态内部保持统一，优先遵循该语言的官方风格指南或社区事实标准**。

#### 类、接口、类型：PascalCase

几乎所有面向对象语言（Java、C#、TypeScript、Python 等）都使用 **PascalCase** 命名类、接口、类型和枚举。

一些常见的**后缀/前缀约定**，能进一步提升可读性：

- **接口**：部分团队使用 `I` 前缀（`IUserRepository`），也有团队（如现代 TypeScript 社区）倾向不加前缀，仅用 PascalCase。关键是团队内部统一。
- **抽象类**：`Abstract` 或 `Base` 开头（`AbstractPaymentMethod`）。
- **异常类**：`Exception` 结尾（`PaymentException`）。
- **测试类**：被测类名 + `Test`（`UserServiceTest`），而非 `TestUserService`。

#### 常量：UPPER_SNAKE_CASE

全局常量、环境变量、枚举值通常使用**全大写 + 下划线**，以在视觉上与普通变量形成强烈区分。

局部常量（作用域很小的常量）可以灵活处理，许多规范允许使用 `camelCase`，避免过度“重音”。

#### 布尔变量：使用语义前缀

布尔变量/属性推荐使用 **`is` / `has` / `can` / `should`** 等前缀，让含义在调用处一目了然：`isActive`、`hasPermission`、`canRetry`、`shouldRefresh`。

**一个重要的框架级例外**：在 **Java 的 POJO 类**中，阿里规约强制要求布尔类型**不要加 `is` 前缀**。原因是部分 RPC/序列化框架在反向解析时，会将 `isDeleted` 错误地映射为 `deleted`，导致属性获取失败。如果项目使用这类框架，需要遵循此约定，或通过手动映射解决。

---

### 三、文档文件

普通文档（`.md`、`.txt` 等）遵循文件命名的总原则：**kebab-case**（`installation-guide.md`、`api-reference.md`）。

例外同样是社区标准文件（`README`、`LICENSE`、`CHANGELOG` 等），保留大写。文档文件名应**体现内容职责**，避免 `doc1.md`、`notes.md` 这类无法从名称判断用途的命名。

---

### 四、几条贯穿所有场景的通用原则

1. **一致性优先于“最优选择”** ：如果你在一个已有项目中工作，先观察现有代码的主流风格。在 `snake_case` 的 Python 项目里，文件夹用 `kebab-case` 可能反而制造割裂感；在已有大量 `camelCase` 文件名的 JS 项目中，全面改造为 `kebab-case` 会丢失 Git 历史。Google 的风格指南也指出，如果目录中已有大量下划线文件，为保持一致，新文件使用下划线是可以接受的。
2. **描述性优于简短**：避免无意义缩写。`getUserProfile` 优于 `getUsrPrf`，`MAX_RETRY_ATTEMPTS` 优于 `MRA`。阿里规约明确将“杜绝不规范缩写”列为强制项。
3. **避免拼音与英文混用**，更不允许直接使用中文命名。
4. **不要在标识符中使用连字符**：`kebab-case` 适用于**文件系统路径**，但连字符在几乎所有编程语言中都是减号，不能用于变量、函数、类名。

---

**一句话总结**：**文件/文件夹默认全小写 + 连字符（特殊文件与语言生态例外除外）；代码符号中，变量/函数跟随语言主流（JS/Java 用 camelCase，Python/Rust 用 snake_case），类用 PascalCase，常量用 UPPER_SNAKE_CASE，布尔加语义前缀（注意 Java POJO 的框架例外）。** 最终落地时，把这份规则写入项目的 `CONTRIBUTING.md` 或 lint 配置，让约定可执行、可检查，比单纯“知道规范”更重要。


# 数字前缀命名规范
你看到的 `01_Active` 这类数字前缀，核心目的只有一个：**在只能按“字典序”排序的文件系统中，强制注入一个有意义的顺序**。它和之前讨论的大小写、连字符问题处在不同维度——前者解决的是“如何分隔单词”，数字前缀解决的是“谁先谁后”。

---

### 为什么需要数字前缀：字典序的“盲区”

绝大多数文件管理器、Shell 通配符展开、Git 平台的文件列表，默认按**字母/字典序（lexicographic order）** 排列文件名，而不是人类直觉的数值顺序。这会导致一个反直觉的结果：

> `10-file.md` 会排在 `2-file.md` **前面**，因为系统逐字符比较，“1”在“2”之前。

数字前缀配合**前导零（zero-padding）** ，就是为了绕过这个“盲区”。把 `1` 写成 `01`、`2` 写成 `02`，字典序就恰好等于数值序。如果没有补零，数字前缀在跨过 9 或 99 时就会失效。

---

### 典型应用场景

数字前缀并非一种“通用风格”，而是一种**有明确目的的工具**。它主要出现在以下几类场景中：

#### 文档与教程：反映阅读或学习顺序

在 MkDocs、Sphinx 等文档生成工具中，数字前缀常被用来驱动导航栏的排序，而不必在配置文件中逐个指定顺序。教程类仓库同样如此：用 `01-basic` 到 `09-crud-api` 给示例目录编号，让文件系统列表天然匹配“由浅入深”的学习路径。

#### 配置与资源清单：控制加载或创建顺序

Linux 的 `/etc/rsyslog.d/` 目录下的 `00-iptables.conf`、`30-haproxy.conf`，依赖文件名字典序来决定配置加载顺序。Kubernetes 的 YAML 清单也常见 `00-namespace.yaml`、`10-deployment.yaml` 这类前缀，目的是在 `kubectl apply -f k8s/*` 时确保命名空间先于工作负载创建，因为 `kubectl` 本身**不会**智能推断资源依赖顺序。

#### 数据处理与迁移：版本或步骤序号

数据库迁移脚本（如 Goose）用数字前缀作为“版本号”，确保迁移按顺序执行。数据流水线中，脚本也可能用 `01_extract`、`02_transform`、`03_load` 来标示执行阶段。

#### 分步工作流：真实的有序步骤

在治理严格的文档体系或工作流模块中，存在一个更精细的约定：**只有当文件本身就是有序序列中的一个“真实步骤”时，才保留数字前缀**。如果数字只是“分割后的序号”或与名称中已有的编号冲突，则应剥离前缀，把排序职责交给父级索引。这意味着数字前缀的合法性来自于“顺序本身是领域的一部分”，而不是为了“看起来整齐”。

#### 领域建模：用编号表达状态或阶段的生命周期

你看到的 `01_Active` 属于另一类用法：**编号本身就是领域概念的一部分**。例如用 `00_Archive`、`01_Active`、`02_Complete` 来表示记录的生命周期阶段，编号既强制了排序，也编码了状态机的流转顺序。`02_STATIC`、`03_ACTIVE` 的目录结构也属于此类，用编号来区分资源类型或代码区域的功能层级。

---

### 格式约定：补零位数与分隔符

一旦决定使用数字前缀，需要明确两件事：

**1. 补零到几位？** 取决于预估的序列规模。如果最多不超过 99 个条目，两位（`01`–`99`）足够；预计到 999 则用三位；数据库迁移甚至使用 14 位时间戳前缀来保证全局唯一且可排序。规则是：**一次性选定足够覆盖未来最大值的位数，之后不要中途加宽**，否则旧文件和新文件的排序会断裂。

**2. 数字和名称之间用什么分隔？** 常见的有 `_`（`01_Active`）、`-`（`01-basic`）以及直接拼接（`0013_slug`）。在代码仓库中，数字前缀通常与已有的文件命名风格衔接：如果项目整体用 kebab-case 命名文件，编号目录常用 `NN-kebab-case` 的形式；如果项目采用下划线风格，则 `NN_snake_case` 也合理。**关键不是哪个分隔符“正确”，而是与项目既有约定保持一致**。

---

### 决策原则：什么时候该用，什么时候不该用

数字前缀的代价是牺牲了纯字母序的可读性和可维护性：每次插入新步骤都可能需要重命名后续文件。因此建议在以下条件下才引入：

| 该用 | 不该用 |
|---|---|
| **顺序是领域语义的一部分**（教程章节、迁移版本、工作流步骤、生命周期阶段） | 顺序只是“我想让列表好看一点” |
| 消费方**只能按字典序读取**，无法从元数据获知顺序 | 父级索引、配置文件或工具已经能显式表达顺序 |
| 序列**相对稳定**，插入/删除不频繁 | 序列会频繁在中间插入条目，重命名成本过高 |
| 位数和分隔符**在项目内全局统一** | 同一棵树里混用 `1_`、`01-`、`001.` 等多种格式 |

对于一般的业务代码目录（`auth/`、`billing/`、`orders/`），**不需要**数字前缀——字母序已经足够，领域概念本身不依赖编号来理解。数字前缀是一个**有代价的排序工具**，只在字典序约束与领域顺序发生冲突时才有必要动用。

**一句话总结**：`01_Active` 这类命名是用**补零数字前缀**在字典序文件系统中强制实现有意义的顺序；它适用于教程步骤、迁移版本、配置加载顺序、工作流阶段等“顺序本身就是语义”的场景，前提是**位数统一、分隔符一致，且顺序相对稳定**。在普通业务目录中，继续使用纯 kebab-case 即可，不必为了整齐而引入编号。

# 数字前缀与名称格式统一
**不是“数字后的符号必须和名称内部的分隔符完全一致”，而是“同一个名字里不要混用分隔符，并且数字前缀的分隔符要服从项目既有的命名风格”。**

逐个看你的例子：

| 命名 | 判断 | 原因 |
|---|---|---|
| `01_Active_Project` | ✅ 可以，前提是项目用 snake_case | 全名下划线统一，没有混用 |
| `01-active-project` | ✅ 更推荐用于普通文件/文件夹 | 全名 kebab-case 统一，跨平台稳妥 |
| `01_active_project` | ✅ 可以 | 全名下划线统一，适合 Python 风格项目 |
| `01_ActiveProject` | ⚠️ 可读但风格略混 | 数字后用 `_`，名称内部无分隔符；不算“混用两种分隔符”，但前缀和名称的视觉边界不够统一 |
| `01-ActiveProject` | ⚠️ 可接受但不算最佳 | 数字后用 `-`，名称是 PascalCase 无分隔符；没有混用分隔符，但“连字符 + PascalCase”不是典型文件命名风格 |
| `01_Active-Project` | ❌ 不合适 | 同一个名字里同时出现 `_` 和 `-`，明显混用分隔符，可读性和一致性都差 |

所以你的核心判断是对的：

> **`01_Active-Project` 这种“数字后下划线、名称内部连字符”是最应该避免的，因为同一个标识符里混用了两种分隔符。**

但 `01-ActiveProject` 并不因为“数字后是 `-`、名称内部没有分隔符”就坏；它的问题是**整体风格不够统一**，而不是“混用分隔符”。更准确的说法是：

1. **一个名字内部只选一种分隔符**：要么全 `_`，要么全 `-`，不要 `01_Active-Project`。
2. **数字前缀的分隔符应与名称内部分隔符一致**：  
   - 名称用 `_` → `01_active_project`  
   - 名称用 `-` → `01-active-project`
3. **如果名称内部没有分隔符**（如 `ActiveProject`），数字后可以加分隔符形成边界，但最好让整体风格和项目一致：  
   - 文件/文件夹默认更推荐 `01-active-project`，而不是 `01-ActiveProject`
   - 如果是领域枚举值或展示名，`01_ActiveProject` 也可接受，但项目内要统一
4. **数字前缀本身不是必须用分隔符**：`01ActiveProject` 能排序，但可读性差，一般不推荐；`01-active-project` 或 `01_active_project` 更清晰。

一句话总结：**`01_Active_Project` 和 `01-active-project` 好，是因为全名分隔符统一；`01_Active-Project` 不好，是因为混用了 `_` 和 `-`。`01-ActiveProject` 不算错，但不是文件命名的最佳风格——文件/文件夹优先用全小写 kebab-case，Python 生态用 snake_case，关键是项目内统一。**

# DSH文件命名规范
在 DSH（DeepSeek Harness）生态下开发跨平台软件，文件与文件夹的命名有一个非常明确且与你之前讨论的原则高度契合的基准规则：**默认使用全小写 + 连字符的 `kebab-case`**。这既是 DSH 社区规范的要求，也是规避跨平台文件系统差异的最稳妥选择。

### 📁 文件夹与一般文件：默认使用 `kebab-case`

对于绝大多数文件夹和普通文件，规则很直接：**全小写，单词间用连字符 `-` 分隔**。

**为什么这是 DSH 跨平台开发的首选：**

- **DSH 社区标准明确要求**：在 DSH 插件开发规范中，文件命名被直接指定为 `kebab-case`。这已经是生态内的既定约定。
- **彻底规避大小写敏感问题**：Linux 文件系统区分大小写，而 Windows 默认不区分。`UserProfile` 和 `userprofile` 在 Linux 上是两个文件，在 Windows 上却可能冲突，导致 Git 合并混乱或构建失败。`kebab-case` 从根源上消除了这个跨平台隐患。
- **可读性与一致性**：连字符被搜索引擎和各类工具普遍识别为单词分隔符，且小写路径在脚本、命令行和 URL 中处理起来最不易出错。

**好的命名**（参考 DSH 与跨平台实践）：
```
components/
  button.tsx
  file-dropzone.tsx
  user-profile.tsx
hooks/
  use-file-upload.ts
lib/
  compose-refs.ts
docs/
  installation-guide.md
  api-reference.md
```

**应当避免的命名**：
```
components/UserProfile.vue      // 大小写混杂，跨平台风险
components/Form_Item.vue        // 混用下划线，风格不统一
docs/Install Guide.md           // 包含空格，在脚本/URL中易出问题
```

### 🧩 需要了解的 DSH 特有例外与约定

`kebab-case` 是**文件/文件夹层面的默认规则**，但在 DSH 生态内，有几种情况需要根据上下文调整：

1. **组件文件可以考虑 PascalCase**：DSH 规范同时提到“组件文件 PascalCase”。如果你的项目重度使用 React/Vue 组件，且团队约定用文件名直接映射组件名（如 `UserProfile.tsx`），这是可以接受的局部例外。但**文件夹仍建议保持 `kebab-case`**，以维持跨平台安全性。
2. **包名遵循 npm scope 规范**：如果你在开发可分发的 DSH 插件/包，其**包名**（`package.json` 中的 `name`）应使用 `@scope/dsh-<domain>-<role>` 的形式，如 `@yourorg/dsh-token-usage`。这是 npm 生态的约定，而非文件系统命名。
3. **特殊社区文件保留大写**：`README.md`、`LICENSE`、`CHANGELOG.md` 等标准文件，保留其全大写惯例。
4. **目录层级引用注意**：DSH 核心目录 `$DSH_HOME` 下的插件目录名，要求**逐字等于包名**（例如 `dsh-plugin-debugging`）。这是运行时解析的要求，开发时需注意。

### 🔢 数字前缀在 DSH 中的使用判断

在 DSH 跨平台开发中，数字前缀的规则不变：**只在“顺序本身是领域语义的一部分”时使用**（如教程步骤、迁移脚本、有序的工作流阶段）。

如果决定使用，**必须与 `kebab-case` 基准规则保持风格统一**：

- **推荐**：`01-active-project`（全小写 + 连字符，数字和名称都用 `-` 分隔）。
- **避免**：`01_Active-Project`（混用 `_` 和 `-`），或 `01_ActiveProject`（与 `kebab-case` 基准风格不一致，在 DSH 生态中会显得突兀）。

### 💎 简单决策清单

| 场景 | 推荐命名 | 关键理由 |
|---|---|---|
| **普通文件夹**（`components/`、`utils/` 等） | `kebab-case` | DSH 规范 + 跨平台安全 |
| **普通文件**（`.ts`、`.md`、`.json` 等） | `kebab-case` | 同上 |
| **组件文件**（React/Vue） | `PascalCase`（局部约定）或 `kebab-case` | DSH 允许组件文件 PascalCase，但需团队统一 |
| **可分发包名** | `@scope/dsh-<domain>-<role>` | npm 生态与 DSH 发布规范 |
| **有序步骤**（需数字前缀时） | `01-kebab-case-name` | 保持与全局 `kebab-case` 风格一致 |
| **社区标准文件** | `README.md` 等保留大写 | 事实标准，不要改动 |

**一句话总结**：在 DSH 下做跨平台开发，**文件夹和一般文件默认就用全小写 + 连字符的 `kebab-case`**，这是生态内最省心、最安全的选择；组件文件可按团队约定局部使用 PascalCase，但不应让大小写混杂的命名出现在路径层面。
