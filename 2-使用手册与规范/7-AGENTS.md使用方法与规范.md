# `AGENTS.md`使用方法与规范

## 基础使用方法

> 只写规则，不堆教程

DSH 按**全局 → 项目根 → 子目录**的顺序加载 `AGENTS.md`，越具体的规则优先级越高。你的项目根 `AGENTS.md` 应当保持短小，只写**每次会话都必须遵守的硬规则**。一个针对待办软件起步阶段的示例：

```markdown
# 项目指令

## 硬规则
- 不要修改 docs/contracts.md 中 TodoItem 的字段语义，除非先提出并获确认。
- 任何功能改动完成后，必须更新 docs/PROGRESS.md 和 docs/TODO.md。
- 不要引入新的状态管理库或持久化库，当前技术栈已锁定。

## 开工顺序
每个新会话开始时，依次读：
1. docs/PROGRESS.md
2. docs/TODO.md
3. docs/architecture.md（如果本次涉及跨模块改动）

## 命令约定
- 包管理器：pnpm
- 测试命令：pnpm test
- 提交信息格式：type: 简短说明（type 用 feat/fix/refactor/docs/chore）

## 风格
- 组件文件名用 PascalCase，工具函数用 camelCase。
- 不要在 UI 组件中直接写存储逻辑，必须经过状态层。
```

**关键纪律**：`AGENTS.md` 是**约束**，不是教程。10 行能说清的规则不要写成 100 行。“不要修改 `contracts.md` 的类型语义”比“请务必注意保持类型一致性”有效得多，**禁止类规则 Agent 执行得更稳**。详细的架构说明、设计理由、操作步骤，全部放在 `docs/` 对应文件里，`AGENTS.md` 只负责“叫 Agent 去读”和“守住底线”。

如果未来某个子目录（比如 `src/platform/`）有独立的平台适配规则，可以在该目录下放一份子级 `AGENTS.md`，只写该子树特有的约束，**不重复根文件已经写过的内容**。DSH 的治理逻辑是“就近治理”，规则放在离它生效位置最近的地方。

## 扩展方法:条件调用

> AGENTS.md中一定不能写入大量文字，所以可以使用跳转的形式在需要的时候定位到相关内容.
> 但是需要注意，它的可靠性不如插件强制注入稳定，但完全符合你“只在创建文件时才读”的要求，且不增加任何会话启动时的上下文开销。

**举例：文档结构：**

> 这里仅为举例说明，建议按照文档结构与使用规范中的内容操作。

- 将具体的文档结构写入`architecture.md`，放入docs目录。
- AGENTS中写入：

  ```markdown
  ## 文件放置规则
  当需要创建任何文件夹或文档时，必须先使用读取 `docs/architecture.md`，然后严格按其中的路径与命名约定执行。禁止凭记忆或推测决定文件位置。
  ```

## 扩展方法:分级管理。规则就近放置，利用目录级 AGENTS.md

如果 architecture.md 的规则主要约束的是某个特定目录（比如 src/features/ 下的文件结构），更优雅的做法是把规则直接放到那个子目录的 AGENTS.md 里，或者放一份精简版在那里。DSH 原生只会自动加载从项目根到当前工作目录链上的 AGENTS.md。当 Agent 的工作范围触及该子目录时，规则才会被自然带入上下文——这本身就是一种基于工作范围的“按需加载”，不需要任何插件。

## 扩展方法：AGENTS.local

> 该方法是利用AGENTS.local作为本地扩展。可以直接作为文件，即「条件调用」方法，也可以成为目录，即「分级管理」方法

### AGENTS和AGENTS.local的区别与使用建议

`AGENTS` 和 `AGENTS.local` 是AI编程代理（Coding Agent）用于读取指令和记忆的两种配置文件。它们的核心区别在于 **“共享”与“私有”**：`AGENTS.md` 是提交到仓库、供团队共享的规则，而 `AGENTS.local.md`（或 `AGENTS.local/` 目录）是存在于本地、被 Git 忽略的个人配置。

#### 📊 核心区别一览

| 特性 | `AGENTS.md` (共享) | `AGENTS.local.md` / `AGENTS.local/` (私有) |
| :--- | :--- | :--- |
| **主要用途** | 团队共享的项目规则、架构指南和硬性约束 | 个人的工作偏好、本地环境配置、详细工作流或历史笔记 |
| **版本控制** | **会提交**到 Git 仓库，是项目的一部分 | **应添加到 `.gitignore`**，刻意不提交，仅保留在个人机器上 |
| **内容定位** | **常驻的“索引”与“红线”**：中等长度（建议 80-200 行），包含每次会话都必须知道的全局信息 | **按需的“细节库”**：存放长流程、大命令块、排错记录等非每时每刻都需要的信息 |
| **典型内容** | 项目目的、目录结构、安全规则、Git 规范、测试构建命令 | 个人偏好的包管理器（如 `pnpm`）、本地数据库端口、个人测试习惯、详细的部署步骤 |
| **加载方式** | 会话开始时**自动加载**，作为基础上下文 | 与 `AGENTS.md` **一同加载**，或由 `AGENTS.md` 中的索引指引，在需要时读取详细内容 |

#### 💡 设计理念：两层结构，平衡上下文效率

这种设计源于一个务实的考量：AI 代理的上下文窗口是有限的资源。将所有信息都塞进一个共享文件，会浪费每次会话的“脑力”在低频信息上。

因此，推荐的做法是采用**两层结构**：

1. **`AGENTS.md` 作为“入口”**：保持精炼，只放必须常驻的规则和一张“导航图”，告诉代理在什么情况下应该去查阅 `AGENTS.local/` 下的哪个具体文件。
2. **`AGENTS.local/` 作为“详情库”**：将详细的工作流、命令示例、历史教训等拆分到该目录下的不同主题文件中，实现**按需加载**。

一个简单的判断法则是：**如果一条信息不是每次对话都必须知道，就应该优先放入 `AGENTS.local/`**。

#### 📝 补充说明

`AGENTS.local` 可以是一个文件（`AGENTS.local.md`），也可以是一个目录（`AGENTS.local/`）。当内容较多时，用目录来组织多个主题文件是更清晰的做法。此外，类似的模式也存在于其他工具中，例如 Claude Code 使用 `CLAUDE.md` 和 `CLAUDE.local.md`，其核心逻辑是完全一致的。

### 如何实现“将AGENTS作为‘入口’，AGENTS.local作为‘详情库’”

要把 `AGENTS.md` 变成一张高效的“导航图”，核心在于完成一次思维转换：**它不是一个“知识仓库”，而是一个“路由表”**。它不负责存储所有细节，只负责根据代理即将执行的任务，告诉它“应该去读哪个文件”。

#### 第一步：设计 AGENTS.md 的“导航图”结构

一份精炼的入口文件通常在 **80-200 行**之间。它的主体应该是一张清晰的**任务-文档路由表**，而不是大段的叙述。你可以直接在 `AGENTS.md` 中使用 Markdown 表格来构建这张地图。

| 当你需要… | 读取文件 | 为什么/何时读 |
| :--- | :--- | :--- |
| 了解项目全貌和架构决策 | `AGENTS.local/00_project_overview.md` | 开始任何新任务前的**必读**背景 |
| 执行本地开发或构建 | `AGENTS.local/05_development_commands.md` | 需要运行、测试或调试代码时 |
| 进行 Git 提交或发布 | `AGENTS.local/06_git_and_release.md` | 准备提交代码或创建发布版本时 |
| 排查某个反复出现的故障 | `AGENTS.local/04_common_pitfalls.md` | 遇到已知的“坑”或错误模式时 |
| 修改特定子系统（如 `auth/`） | `AGENTS.local/08_auth_subsystem.md` | **仅当**任务涉及该子系统时读取 |

这种表格格式的优势在于其**条件触发**的逻辑。它明确告诉代理：“**当**（When）你处于某个场景，**就去**（Where）读这个文件”。这比单纯列出文件列表要高效得多，因为它直接关联了“意图”与“知识”。

#### 第二步：用“渐进式披露”组织 AGENTS.local/

`AGENTS.local/` 目录的组织方式，应该与导航图的粒度保持一致。建议采用**数字前缀+主题**的命名方式，让文件本身就能传达阅读顺序和优先级。

```text
AGENTS.local/
├── 00_project_overview.md      # 项目目的、架构、核心信念
├── 01_repository_layout.md     # 目录结构详解与职责边界
├── 02_core_workflows.md        # 核心业务流程（如用户注册、支付）
├── 03_data_formats.md          # 数据模型、API Schema 约定
├── 04_common_pitfalls.md       # 历史排错记录、已知问题
├── 05_development_commands.md  # 完整的测试、构建、Lint 命令
├── 06_git_and_release.md       # 分支策略、Commit 规范、发布流程
└── 07_long_term_notes.md       # 低频但重要的长期笔记
```

这个结构遵循了**渐进式披露**的原则：代理从稳定的入口（`AGENTS.md`）开始，只有在需要时才沿着导航图深入加载某个具体的 topic 文件，从而避免在会话伊始就淹没在信息中。

#### 第三步：让导航“活”起来——在 AGENTS.md 中加入元规则

仅仅列出文件是不够的。你需要在 `AGENTS.md` 中明确写入**操作指令**，告诉代理如何使用这张导航图。这相当于给代理一个“如何导航”的元规则。

例如，你可以在导航表之后，加上这样一条明确的**硬规则**：

> **知识库查阅规则**：在执行任何非平凡的代码修改前，你必须先根据任务类型查阅上表。例如，若任务涉及数据库迁移，**必须先**读取 `05_development_commands.md` 中的迁移流程；若涉及认证模块，**必须**读取 `08_auth_subsystem.md`。忽略此规则导致的错误将被视为严重失误。

这条规则将“被动”的文件列表，转变成了代理必须执行的**主动工作流**。一些工具甚至支持更结构化的触发机制，比如通过规则文件的 `trigger` 字段来指定“当处理匹配 `**/*.test.ts` 的文件时，自动加载测试规范”。

#### 💎 总结

实现“入口+导航”模式的精髓，不在于 `AGENTS.local/` 里放了多少知识，而在于 `AGENTS.md` 里的那张表**是否清晰地定义了“任务场景”与“知识文件”之间的映射关系**。当你把 `AGENTS.md` 当作一个需要精心设计的**路由协议**，而不是一份随意的备忘录时，它的精炼与高效才会真正显现出来。

## 扩展方法:插件（不推荐）

> 注意这种方法会强制阅读所有连带文件，增加token消耗

利用插件强行注入。它会扫描 AGENTS.md 中的 @路径 引用，把被引用文件的内容真正注入会话上下文，让模型能够看到。
例如`dsh-context-imports`插件.
在AGNETS.md中写入：

```markdown
## 文件与目录规范
@docs/file-placement.md
```

这个插件就会强制要求agent阅读AGENTS.md时连带阅读docs/file-placement.md。
