先给一条消除疑惑的总规则：**同一个问题只查一份文档，查到即停；其他文档最多引用它，不重复写答案。** 下面每个环节都按“文档 → 唯一作用”一一列出。

## 流程中会用到哪些文档

### 会话启动

- `AGENTS.md`
  - 加载项目级规则、文档阅读顺序和“唯一事实源”规则。
- `AGENTS.local.md`
  - 只提供本机覆盖，不进库，不承担项目事实。
- `PROJECT_STATE.md`
  - 这是当前「阶段提醒」
  - 只回答“现在处于什么阶段、是否还在 MVP 内、下一个里程碑是什么”。

### 需求与规划

- `spec.md`
  - 这是总规划，重点在「边界」。
  - 只回答“做什么、不做什么、功能列表、非功能需求、验收目标”。需求边界以它为唯一事实源。
  - `PROJECT_STATE.md` 只写“是否守住边界”的结论，不重复边界列表。
- `plan.md`
  - 这是总计划，重点在「结构」和「顺序」。
  - 只回答：阶段路线、模块依赖、目录设计、技术方案结论。它允许未来时，不负责描述当前骨架。
- `decisions.md`
  - 这是决定日志，重点在「记录」。
  - 只回答“为什么这样定、放弃了什么”。选型原因写这里。
  - `spec.md` 和 `plan.md` 只引用，不展开论证。
- `03_Research/`
  - 只提供验证证据：竞品截图、用户反馈摘录。它不定义需求，只支撑需求。

### 任务选择

- `tasks.md`
  - 这是当前迭代的「原子任务清单」。
  - 只回答“当前迭代先做什么、后做什么、P0/P1 是什么”。下一步做什么只看它。
  - `plan.md` 管阶段路线，`tasks.md` 管当前迭代怎么落地。
- `TODO.md`
  - 是一份「备选任务清单」
  - 只回答“跨迭代还有什么没做、哪些已完成、哪些搁置”。
  - 只有 `tasks.md` 空了，才来这里挑任务。
- `PROGRESS.md`
  - 是当前迭代的轮次「状态日志」
  - 只回答“每轮完成了什么、卡在哪、下一步是什么”。它记录状态，不复制任务全文。
  - 比 `PROJECT_STATE.md` 更细颗粒度地描述“做到哪”，但只记录状态，不定义任务
  - `PROJECT_STATE.md` 才是项目级阶段快照。

### 执行前约束

- `architecture.md`
  - 只回答“当前系统骨架长什么样、目录和模块现在是什么关系”。判断现状只看它，不看 `plan.md`。
- `contracts.md`
  - 只回答“TodoItem 等核心类型的字面形状和语义是什么”。字段定义以它为唯一事实源，`checklist.md` 只引用，不重复定义。
- `conventions.md`
  - 只回答“命名、提交格式、代码风格有哪些硬规则”。风格问题只看它，不看 `contracts.md`。
- `DEBT.md`
  - 只回答“已知脆弱点、临时方案、技术债在哪里”。执行前扫一眼，避免踩已知坑。

### 验收

- `checklist.md`
  - 只回答“做成什么样才算合格”：可勾选的验收判据、DoD、异常处理要求。逐条自查只看它。
- `tests/`
  - 只负责自动化验证的实现和运行结果。它不定义合格标准，标准在 `checklist.md`。

### 阶段收尾记录

- `PROGRESS.md` → 写本轮进度和状态，回答“这轮做完了什么、卡在哪”。
- `tasks.md` → 只改任务状态：勾选完成、调整顺序、标记阻塞。
- `TODO.md` → 只收纳未完成任务、搁置项和新冒出来的 backlog。
- `decisions.md` → 只记录本轮产生的新决策和放弃的方案。
- `DEBT.md` → 只登记本轮新增的临时方案和技术债。

### 里程碑与发布

- `PROJECT_STATE.md` → 只更新阶段、MVP 边界结论、下一里程碑。里程碑收尾时写它。
- `02_Design/` → 只提供 UI 设计源文件和导出素材，UI 任务按需使用。
- `04_Operations/` → 只提供上架文案、截图、定价笔记。
- `05_Legal/` → 只提供隐私政策、条款。
- `06_Releases/` → 只存放构建产物，`.gitignore` 排除。

## 哪些文档可以作为统括文档

统括的意思是：**项目简单时，把多份文档合并成一份，被并入的文档不再单独存在，避免双事实源。** 不是“两份都写，一份当摘要”。

- `spec.md` 可以统括 `checklist.md`：
  - 在 `spec.md` 末尾加“验收标准”章节，把 `checklist.md` 的判据逐条放进去。
  - 简单项目不再单独维护 `checklist.md`。需求边界和验收标准同源，反而更清楚。
- `spec.md` 可以统括 `PROJECT_STATE.md`：
  - 极简项目可以把“当前阶段”作为 `spec.md` 的一节。
- `plan.md` 可以统括 `architecture.md`：
  - 在 `plan.md` 里加“当前架构”章节。
  - 但要注意：`plan.md` 主体是未来规划，这一章是现在时，标题写清楚“当前架构（现在时）”。项目变大后再拆出独立 `architecture.md`。
- `contracts.md` 可以统括 `conventions.md`：
  - 在 `contracts.md` 里加“命名与风格硬规则”章节。
  - 类型契约和风格规则都是编码前要查的硬约束，小项目合在一起查一次就够。
- `tasks.md` 可以统括 `TODO.md` 和 `PROGRESS.md`：
  - 在 `tasks.md` 里加“Backlog/搁置”章节和“状态/日志”列。
  - 简单项目一个文件就能回答“下一步做什么、还有什么没做、做到哪了”。项目变大、多轮会话频繁时再拆出 `PROGRESS.md`。
- `decisions.md` 可以统括 `DEBT.md`：
  - 在 `decisions.md` 里加“技术债”章节。
  - 决策和债都是“为什么现在这样、以后要还什么”，小项目合在一起合理。

统括后的原则：**合并了就删掉被合并文件，并在 `AGENTS.md` 和 `00_README.md` 里更新阅读路径。** 不要保留空文件或“摘要版”。

## spec和project_state的区别

一句话区别：**`spec.md` 定义“要造什么、不造什么、做到什么程度算符合需求”；`PROJECT_STATE.md` 记录“现在造到哪、当前阶段是否还守在这个范围内、下一个里程碑是什么”。** 前者是需求宪法，后者是阶段快照。

---

### 1. 它们各自回答的问题不同

`spec.md` 回答的是**需求问题**：

- 这个产品为什么存在？目标用户是谁？
- MVP 包含哪些功能？明确不包含哪些功能？
- 非功能需求是什么，比如性能、安全、离线、隐私？
- 每个功能的验收目标是什么？
- 这个需求该不该做？做到什么程度算符合需求？

`PROJECT_STATE.md` 回答的是**阶段问题**：

- 项目现在处于哪个阶段？原型、MVP 开发、MVP 验收、公测、发布？
- 当前阶段是否仍然只做 MVP？有没有范围膨胀？
- 当前里程碑是什么？下一个里程碑是什么？
- 距离下一个里程碑还差哪些 `spec.md` 里的条目？
- 当前有没有阻塞、风险、需要人类决策的事项？

所以：

- 问“**要不要做**” → 查 `spec.md`。
- 问“**现在该不该做、先做到哪**” → 查 `PROJECT_STATE.md`。

---

### 2. 内容边界不同

`spec.md` 写的是**长期稳定的需求事实**：

- 背景与目标
- 用户与场景
- 功能列表，包括 MVP 内和范围外
- 非功能需求
- 数据模型的需求级描述，具体类型字面形状引用 `contracts.md`
- 验收目标，具体可勾选判据可以引用或并入 `checklist.md`
- 明确“不做什么”

`spec.md` 不写：

- 当前做到哪了
- 当前迭代先做哪个任务
- 当前有没有阻塞
- 每个阶段的时间安排
- 任务优先级 P0/P1 的执行顺序

`PROJECT_STATE.md` 写的是**当前阶段的快照**：

- 当前阶段名称和判断依据
- 当前 MVP 边界结论：是“仍在 MVP 内”还是“已进入扩展阶段”
- 当前里程碑和下一个里程碑
- 当前里程碑对应 `spec.md` 的哪些条目，只写条目编号或引用，不复制功能列表
- 当前阻塞、风险、需要人类决策的事项
- 最近一次阶段评审结论

`PROJECT_STATE.md` 不写：

- 完整功能列表
- 详细需求背景
- 具体任务拆解
- 每轮进度日志
- 类型字段定义
- 代码风格规则

---

### 3. “MVP 边界”为什么两边都会出现？怎么分工？

这是最容易混淆的地方。`spec.md` 和 `PROJECT_STATE.md` 都可能出现“MVP 边界”，但职责不同：

- `spec.md` 定义 **MVP 边界的内容**：MVP 包含 A、B、C，不包含 D、E、F。这是唯一事实源。
- `PROJECT_STATE.md` 记录 **MVP 边界的状态**：当前仍在 MVP 内，范围未膨胀；当前里程碑只交付 A 和 B；C 放在下一个里程碑；D、E、F 继续不做。

也就是说：

- `spec.md` 写“边界在哪里”。
- `PROJECT_STATE.md` 写“我们现在有没有越过边界、下一步走到边界内的哪一段”。

`PROJECT_STATE.md` 不要复制 A、B、C、D、E、F 的完整列表，只写“当前里程碑交付 `spec.md` 的 F1、F2；范围外项不变”。这样只有一个需求事实源。

---

### 4. 更新频率和读者不同

`spec.md`：

- 低频更新，但一旦变更影响大。
- 主要由产品/需求负责人维护。
- 变更时要同步 `decisions.md`，说明为什么改需求、放弃了什么。
- Agent 在判断需求边界、验收目标时读它。

`PROJECT_STATE.md`：

- 每个阶段或里程碑更新一次，属于低频但比 `spec.md` 稍频繁。
- 主要由项目负责人或人类维护。
- Agent 在每次会话启动时读它，用来判断当前阶段和下一步方向。
- 它不记录每轮进度，每轮进度在 `PROGRESS.md`。

---

### 5. 用 Todo App 举例

`spec.md` 里写：

- MVP 功能：新增 Todo、删除 Todo、修改 Todo、标记完成、按状态筛选、本地持久化。
- MVP 不做：用户登录、多人协作、提醒通知、云同步、导出。
- 非功能：本地优先、刷新不丢数据、错误输入不能导致崩溃。
- 验收目标：输入空标题必须提示，不能创建空 Todo；刷新后数据仍在。

`PROJECT_STATE.md` 里写：

- 当前阶段：MVP 开发中。
- MVP 边界结论：仍只做 `spec.md` 中列出的 MVP 功能，登录、协作、提醒、云同步、导出继续不做。
- 当前里程碑：MVP-1 基础 CRUD 可运行。
- 下一里程碑：MVP-2 筛选与本地持久化。
- 当前差距：`spec.md` 的 F1-F4 已可用，F5-F6 未开始。
- 阻塞：无。
- 需人类决策：无。

这时：

- 有人问“能不能加提醒通知？” → 查 `spec.md`，结论是范围外，不做。
- 有人问“现在先做提醒还是先做筛选？” → 查 `PROJECT_STATE.md` 和 `tasks.md`，当前里程碑先做基础 CRUD，下一里程碑才做筛选，提醒不在当前阶段。
- 有人问“MVP 完成标准是什么？” → 查 `spec.md` 的验收目标，具体勾选查 `checklist.md`。
- 有人问“我们是不是已经偏离 MVP 了？” → 查 `PROJECT_STATE.md` 的边界结论。

---

### 6. 查文档的口诀

可以记成三句话：

1. **需求该不该做、做到什么程度：查 `spec.md`，查到即停。**
2. **现在处于什么阶段、下一步走到哪、是否越界：查 `PROJECT_STATE.md`，查到即停。**
3. **如果两份文档看起来冲突：需求内容以 `spec.md` 为准；`PROJECT_STATE.md` 只是阶段快照，错了就修正快照，不让它反过来改需求。**

更细的判断顺序：

- 问“这个功能在不在范围内” → `spec.md`
- 问“这个功能现在做不做” → `PROJECT_STATE.md` + `tasks.md`
- 问“这个功能验收标准是什么” → `spec.md` 的验收目标，或并入的 `checklist.md`
- 问“当前里程碑还差什么” → `PROJECT_STATE.md`
- 问“今天先干哪个任务” → `tasks.md`
- 问“上一轮做到哪” → `PROGRESS.md`

---

### 7. 常见误区

- 误区一：在 `PROJECT_STATE.md` 里复制完整功能列表。结果是需求一改，两份都漂移。正确做法是只写“当前里程碑交付 `spec.md` 的哪些条目”。
- 误区二：把 `spec.md` 写成进度日志。`spec.md` 不记录“今天做到哪”，那是 `PROGRESS.md` 和 `PROJECT_STATE.md` 的事。
- 误区三：用 `PROJECT_STATE.md` 判断需求该不该做。阶段快照不能替代需求宪法；范围问题回到 `spec.md`。
- 误区四：两份都写“MVP 边界”且都写完整清单。只保留 `spec.md` 的清单，`PROJECT_STATE.md` 只写状态结论和引用。

---

### 8. 项目极简时怎么统括

如果项目很小，可以合并，但**合并后只保留一份，不要两份都写**：

- 方案 A：保留 `spec.md`，把 `PROJECT_STATE.md` 降为 `spec.md` 开头的一节“当前阶段快照”。合并后删除 `PROJECT_STATE.md`，阶段问题查 `spec.md` 这一节。
- 方案 B：保留 `PROJECT_STATE.md`，但它只写阶段快照，需求边界仍完整放在 `spec.md`。这是“不合并但分工清楚”，适合小团队。
- 不推荐：两份都保留，且两份都写完整 MVP 功能清单。这就是“重复维护”。

一句话收束：**`spec.md` 管“边界内容”，`PROJECT_STATE.md` 管“边界状态”；需求问题只查 `spec.md`，阶段问题只查 `PROJECT_STATE.md`。**

## “做什么”和“验收标准”放哪里

- “功能 A、功能 B 具体是什么”放在 `spec.md`；
- “第一阶段做什么、第二阶段做什么”这种阶段路线放在 `plan.md`。只做“阶段序列 + 引用”，不复制功能和判据；
- “验收标准 1、2、3 的具体判据”放在 `checklist.md`（或并入 `spec.md` 的验收章节）；
- “现在走到第几阶段”放在 `PROJECT_STATE.md`。

### 1. 你举的例子应该怎么拆

你描述的“第一阶段开发功能 A，验收标准 1、2、3；第二阶段开发功能 B，验收标准 4、5、6”，实际上混了四类信息：

| 信息                               | 归属文档             | 写法                                               |
| ---------------------------------- | -------------------- | -------------------------------------------------- |
| 功能 A、功能 B 是什么、范围边界    | `spec.md`          | 完整定义 F-A、F-B，写明做什么、不做什么            |
| 第一阶段做 A、第二阶段做 B 的顺序  | `plan.md`          | 阶段路线：Phase 1 → 交付 F-A；Phase 2 → 交付 F-B |
| 验收标准 1、2、3 的具体判据        | `checklist.md`     | AC-A1、AC-A2、AC-A3 可勾选判据                     |
| 当前处于第几阶段、Phase 1 还差什么 | `PROJECT_STATE.md` | 状态快照：当前 Phase 1，F-A 未验收                 |
| Phase 1 内部先做哪个原子任务       | `tasks.md`         | 当前迭代的原子任务和顺序                           |

所以你的例子在文档里应该长这样：

**`spec.md` 里写：**

```markdown
## 功能 A
- 目标：……
- 范围：包含 A1、A2；不包含 A3
- 验收目标：见 checklist.md 的 AC-A1~AC-A3

## 功能 B
- 目标：……
- 范围：包含 B1、B2
- 验收目标：见 checklist.md 的 AC-B1~AC-B3
```

**`plan.md` 里写：**

```markdown
## 阶段路线

### Phase 1：交付功能 A
- 交付范围：spec.md 的 F-A
- 验收关口：checklist.md 的 AC-A1~AC-A3 全部通过
- 退出条件：AC-A 全绿，PROJECT_STATE 更新为 Phase 2

### Phase 2：交付功能 B
- 交付范围：spec.md 的 F-B
- 验收关口：checklist.md 的 AC-B1~AC-B3 全部通过
- 依赖：Phase 1 完成
```

**`checklist.md` 里写：**

```markdown
## 功能 A 验收
- [ ] AC-A1：……
- [ ] AC-A2：……
- [ ] AC-A3：……

## 功能 B 验收
- [ ] AC-B1：……
- [ ] AC-B2：……
- [ ] AC-B3：……
```

**`PROJECT_STATE.md` 里写：**

```markdown
- 当前阶段：Phase 1
- 当前里程碑：交付功能 A
- 差距：F-A 已实现，AC-A1 通过，AC-A2/AC-A3 未通过
- 下一里程碑：Phase 2 交付功能 B
```

这样：

- 问“功能 A 到底做什么” → 查 `spec.md`，查到即停。
- 问“先做 A 还是先做 B” → 查 `plan.md` 的阶段路线，查到即停。
- 问“A 做到什么程度算合格” → 查 `checklist.md` 的 AC-A，查到即停。
- 问“现在到哪了” → 查 `PROJECT_STATE.md`，查到即停。
- 问“今天先干哪个任务” → 查 `tasks.md`，查到即停。

---

### 2. 为什么阶段计划放 `plan.md`，而不是 `PROJECT_STATE.md`

两者都出现“阶段”，但职责完全不同：

- `plan.md` 是**计划态**：项目打算分几个阶段、每个阶段交付什么、阶段之间什么依赖、每个阶段的验收关口是什么。它是蓝图，允许未来时，一次写清楚，后续按需调整。
- `PROJECT_STATE.md` 是**状态态**：现在实际处于哪个阶段、当前阶段还差什么、有没有阻塞、下一个里程碑是什么。它是快照，每个阶段或里程碑更新一次。

判断口诀：

- 问“**计划分几个阶段、每阶段做什么**” → `plan.md`
- 问“**现在在第几阶段、离下一阶段还差什么**” → `PROJECT_STATE.md`
- 问“**当前阶段内部先做哪个任务**” → `tasks.md`

`PROJECT_STATE.md` 不要复制 `plan.md` 的完整阶段路线，只写“当前处于 Phase 1，下一里程碑 Phase 2”，需要细节时引用 `plan.md`。

---

### 3. 验收标准放哪里：`plan.md` 还是 `checklist.md`

分两层，避免重复：

- **阶段级验收关口**放 `plan.md`：写“Phase 1 的退出条件是 AC-A1~AC-A3 全部通过”。它只写“用哪些判据当关口”，不写判据内容。
- **判据内容**放 `checklist.md`：AC-A1 具体是什么、怎么验证、期望结果是什么。它是唯一事实源。
- `spec.md` 只写“功能 A 的验收目标见 checklist 的 AC-A”，不重复判据。
- `PROJECT_STATE.md` 只写“AC-A1 通过、AC-A2/AC-A3 未通过”，不重复判据内容。

项目很小、不想维护 `checklist.md` 时，可以把判据直接并入 `spec.md` 的“验收标准”章节，`plan.md` 仍然只引用“spec 的 AC-A1~AC-A3”。**但只保留一份判据，不要 plan 和 checklist 各写一遍。**

---

### 4. 完整开发计划应该由哪几份文档共同承载

严格说，“整个项目的开发计划”不是一个文件，而是四份文档各管一段：

- `plan.md` → 阶段路线：分几个阶段、每阶段交付哪些功能、阶段依赖、阶段验收关口。
- `spec.md` → 功能内容：每个功能是什么、范围边界、非功能需求。
- `checklist.md` → 验收判据：每个功能/阶段的可勾选合格标准。
- `tasks.md` → 当前阶段执行：当前阶段拆成哪些原子任务、顺序、P0/P1。
- `PROJECT_STATE.md` → 当前状态：现在走到哪、差距、阻塞、下一里程碑。

如果你的“开发计划”指的是“阶段划分 + 每阶段交付范围 + 阶段验收关口”，那主体就是 `plan.md`。其他文档是它引用的目标。

---

### 5. 项目简单时的统括建议

如果项目小，不想拆这么多，可以这样合并，但**合并后只保留一份，不要两边都写**：

- **方案 A（推荐，4 份）**：`spec.md` 统括 `checklist.md`，`plan.md` 统括 `architecture.md`，`tasks.md` 统括 `TODO/PROGRESS`，`decisions.md` 统括 `DEBT`。阶段计划仍在 `plan.md`，验收判据在 `spec.md` 的“验收标准”章节，`plan.md` 阶段条目引用“spec 的 AC-A1~AC-A3”。
- **方案 B（极简，3 份）**：`spec.md` 里加“阶段路线”一节，把 `plan.md` 的阶段计划并进去；再加“验收标准”一节，把 `checklist.md` 并进去；`tasks.md` 管当前任务和进度；`PROJECT_STATE.md` 管当前阶段快照。这时“开发计划”在 `spec.md` 的阶段路线一节，但要注意 `spec.md` 会变重，项目一变大就拆回方案 A。
- **不推荐**：`plan.md` 和 `spec.md` 都写完整功能列表和验收判据；`PROJECT_STATE.md` 又复制一遍阶段路线。这是典型的“重复维护”。

一句话收束：**阶段顺序和每阶段交付范围放 `plan.md`；功能是什么放 `spec.md`；验收判据放 `checklist.md` 或并入 `spec.md`；当前走到哪放 `PROJECT_STATE.md`；当前阶段先做哪个任务放 `tasks.md`。同一个问题只查一份，查到即停。**

## “目录结构”“命名规则”“目录调整规则”放哪里？

建议分三层放，不要只塞进一个文件：

### 结论

**完整目录树和模块职责放 `architecture.md`；`AGENTS.md` 只写“必须遵守目录架构、不得随意新增顶层目录”的硬规则并引用它；`conventions.md` 只写目录/文件命名规则；`plan.md` 只写“未来准备怎么调整目录”，不复制当前目录树。**

如果你问的是“让 Agent 每次会话都必须遵守”的规则，那入口在 **`AGENTS.md`**；如果你问的是“目录架构的完整事实源”，那在 **`architecture.md`**。

---

### 1. 各文件分别放什么

#### `architecture.md`：当前目录架构的唯一事实源

放：

- 完整目录树，当前时
- 每个目录/模块的职责
- 模块之间的依赖关系
- 哪些目录是顶层目录，哪些是子目录
- 新增文件应该放在哪个目录的规则
- 不允许随意新增的目录边界

示例：

```markdown
## 当前目录结构
todo-app/
├── docs/
├── 01_Project/
│   ├── src/
│   │   ├── components/
│   │   ├── pages/
│   │   ├── store/
│   │   └── api/
│   └── tests/
├── 02_Design/
├── 03_Research/
├── 04_Operations/
├── 05_Legal/
└── 06_Releases/

## 模块职责
- src/components：通用 UI 组件
- src/pages：页面级组件
- src/store：状态管理
- src/api：数据访问

## 目录硬边界
- 新增业务代码只能放在 01_Project/src 下
- 不得在根目录新增一级目录，除非更新本文件并记录 decisions.md
```

`architecture.md` 不写：

- 文件叫 `TodoItem.tsx` 还是 `todo-item.tsx` → 查 `conventions.md`
- 以后准备拆成 monorepo 吗 → 查 `plan.md`
- 为什么选这个目录组织 → 查 `decisions.md`

#### `AGENTS.md`：Agent 必须遵守的入口规则

放：

- “开始编码前先读 `architecture.md` 的目录结构”
- “不得随意新增顶层目录”
- “新增目录必须同步更新 `architecture.md`，并在 `decisions.md` 记录原因”
- “文件放置位置以 `architecture.md` 为准”

但**不要**在 `AGENTS.md` 里复制完整目录树，只写规则和引用。示例：

```markdown
## 目录规则
- 当前目录架构以 docs/architecture.md 为唯一事实源。
- 新增业务代码只能放在 01_Project/src 下。
- 不得在项目根新增一级目录；确需新增时，先更新 architecture.md，并在 decisions.md 记录原因。
- 文件命名遵循 docs/conventions.md。
```

这样 Agent 每次会话自动加载 `AGENTS.md`，就知道“目录架构看哪里、不能乱动什么”。

#### `conventions.md`：只放命名和格式硬规则

放：

- 目录名用 kebab-case 还是 snake_case
- 组件文件用 PascalCase，工具函数用 camelCase
- 测试文件放 `tests/` 还是与源文件同目录
- import 顺序、文件组织风格

不放完整目录树。示例：

```markdown
## 目录与文件命名
- 目录名：kebab-case
- React 组件文件：PascalCase.tsx
- 工具函数文件：camelCase.ts
- 测试文件：与源文件同目录，命名为 *.test.ts
```

#### `plan.md`：只放未来目录规划

放：

- 当前阶段准备新增哪些目录
- 以后是否拆 monorepo、是否调整顶层结构
- 目录演进的阶段路线

不放“当前完整目录树”，避免和 `architecture.md` 双事实源。示例：

```markdown
## 目录演进计划
- Phase 1：保持 01_Project/src 单包结构
- Phase 2：如模块增多，将 src/api 拆为独立 package
```

---

### 2. 查询口诀

- 问“**当前目录树是什么、文件该放哪**” → 查 `architecture.md`，查到即停。
- 问“**Agent 必须遵守哪些目录硬规则**” → 查 `AGENTS.md`，查到即停。
- 问“**目录/文件怎么命名**” → 查 `conventions.md`，查到即停。
- 问“**以后准备怎么调整目录**” → 查 `plan.md`，查到即停。
- 问“**为什么这样组织目录**” → 查 `decisions.md`。

---

### 3. 项目简单时怎么统括

如果项目小，不想维护太多文件，可以合并，但**只保留一份目录事实源**：

- 方案 A：`plan.md` 统括 `architecture.md`，在 `plan.md` 里加“当前目录结构（现在时）”一节。适合项目刚起步、架构还没稳定。`AGENTS.md` 仍写目录硬规则并引用 `plan.md`。
- 方案 B：保留 `architecture.md`，把 `conventions.md` 的目录命名规则并入 `architecture.md` 的“命名规则”一节。适合小项目，目录结构和命名一起查。
- 不推荐：`AGENTS.md`、`architecture.md`、`plan.md` 三处都放完整目录树。这是重复维护，最容易漂移。

一句话收束：**完整目录架构放 `architecture.md`；Agent 的遵守规则放 `AGENTS.md` 并引用前者；命名规则放 `conventions.md`；未来调整放 `plan.md`。目录树只维护一份。**

### `docs/contracts.md`：核心类型的唯一事实源

```markdown
# 数据契约

> 本文件中的类型定义是**唯一事实源**。其他文档引用类型时只链接，不复制。
> 修改本文件中的字段语义，需先在会话中提出并获得确认。

## TodoItem

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `id` | `string` | 是 | 稳定唯一标识，创建后不变 |
| `title` | `string` | 是 | 用户输入的标题，非空 |
| `completed` | `boolean` | 是 | 是否已完成 |
```

```markdown
## #3 — 截止日期只到天，不引入时间与时区

**日期**：2026-11-09
**状态**：已接受

### 背景
待办类产品的截止日期在用户直觉中是“今天要做完”，而不是“今天 14:00 前”。
引入时间部分会立刻带来时区转换、跨天边界、显示格式等复杂度。

### 决策
`TodoItem.dueDate` 只存储 `YYYY-MM-DD` 格式的日期字符串，不含时间部分。
过期判定以本地时区的自然日为准。

### 备选方案
- **存完整时间戳**：优点是可以做精确提醒；缺点是 MVP 阶段没有提醒功能，
  引入时间部分只会增加不必要的复杂度。拒绝。
- **存时间戳但 UI 只显示日期**：数据层和 UI 层语义不一致，长期容易出错。拒绝。

### 影响
- 存储和排序逻辑更简单。
- 如果未来需要精确到分钟的提醒，需要一次数据迁移。届时重新记录 ADR。

---

## #2 — 状态管理选 Zustand，不选 Redux

**日期**：2026-11-08
**状态**：已接受

### 决策
使用 Zustand 作为状态管理库。

### 理由
个人项目，UI 状态树不复杂。Zustand 无 Provider 包裹、样板代码少，
Agent 生成代码时出错的表面更小。Redux 的 DevTools 和中间件生态在此规模下是过度设计。

### 备选方案
- **Redux Toolkit**：生态成熟，但对单人 Todo 应用而言配置成本高于收益。拒绝。
- **React Context + useReducer**：够用，但跨组件读写时容易产生不必要的重渲染。拒绝。
```

每条决策控制在 1—2 页内，**只记已经做出的决定，不记讨论过程**。状态用“已接受 / 已弃用 / 被 #N 取代”，弃用的条目保留，不删除——Agent 将来问“为什么不用 X”时，答案在这里。

```markdown
# 技术债务与已知脆弱点

## #1 — 日期选择器跨平台行为未验证
**位置**：`src/ui/DatePicker`
**风险**：macOS 原生 date input 的样式和交互与 Windows 可能存在差异；
移动端（如果未来打包）的行为完全未知。
**当前策略**：MVP 桌面端先使用原生 input，阶段 3 统一验证。
**不要做什么**：不要在这个组件上叠加自定义日期面板，等跨平台验证完成后再决定。

## #2 — 本地 JSON 文件存储在数据量增长后可能变慢
**位置**：`src/persistence/LocalStore`
**风险**：当前每次写入重写整个 JSON 文件。待办项超过数百条时，
写放大可能变得明显。
**当前策略**：MVP 阶段不做优化。如果真实用户数据量触发问题，再评估 IndexedDB 或 SQLite。
```

`DEBT.md` 的用途不是“记录所有不完美”，而是告诉 Agent **哪些地方现在不要动、动了要小心**。每一条带“不要做什么”比带“应该做什么”更有约束力。

```markdown
- React 组件文件：`PascalCase.tsx`（如 `TodoItem.tsx`）
```
